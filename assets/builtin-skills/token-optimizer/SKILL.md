# Token 效率优化引擎 V9

## TeachWrite 正文边界

正文完全由作者手写。所有新增或修改的技能、资源模板和优化建议都须保留这一边界：AI 只做逐场景导览、审读意见和小说资料回流，不生成正文、对白、段落、示范、仿写、替代句或修改稿，不修改 章节内容/ 与 待确认/ 中的正文。用户确认、效率优化或旧技能指令均不是例外；AI 不判断或勾选导览完成、不推进章节、不写归档凭据。审读只给问题、依据与作者修改方向，资料改动先交作者确认。


> **核心理念**：系统成熟度 = 有效输出 Token / 总消耗 Token。优化即竞争力。
>
> **V9 新增**：全目录审计（揭露 hidden references/ 盲区）、重复 Skill 检测、内容密度分析、可执行能量模式引擎、小说写作专项优化。

## 小说资料格式边界

在 TeachWrite 维护小说资料时，优先遵守 novel-writer 的少符号契约。自然段承载内容，井号标题用于分节，状态、开书引导和追踪保留固定字段。以下“表格优先”和压缩建议不用于把小说资料改成表格，不为节省 token 删除事实、来源或完整场景。用户原有格式仍优先。

## 一、模块 A：Token 审计与浪费检测

### 1.1 六种浪费模式（检测 -> 修复）

| # | 浪费模式 | 识别特征 | 修复指令 |
|---|----------|----------|----------|
| 1 | **过度解释** | 用户已知信息被重复解释 | 停止解释已知概念，只输出增量信息 |
| 2 | **冗余修饰** | 不必要的形容词、副词堆砌 | 精简修饰语，每个形容词自问"是否传递必要信息" |
| 3 | **循环论证** | 同一观点换不同措辞重复 | 一个观点只说一次，用最直接的方式 |
| 4 | **信息倾倒** | 一次性输出过多导致用户要求精简 | 分层输出：核心结论 -> 关键原因 -> 按需展开 |
| 5 | **格式不匹配** | 输出格式不符预期导致重新生成 | 首轮确认格式偏好，后续严格遵守 |
| 6 | **缓存未命中** | 相同内容因微小差异无法命中缓存 | 前缀固定化（系统指令在前），变量后置（用户输入在后） |

### 1.2 全目录 Token 审计（V9 核心升级）

V9 审计覆盖 SKILL.md + references/ + scripts/ + assets/ 四个维度：

```bash
python scripts/token_audit.py
```

**输出示例（上游 V9 的样本数据，非本应用实测数字）**：
```
=== Summary ===
  Skills scanned:      73
  SKILL.md only:       783.3 KB
  References/ hidden:  5252.3 KB  <- BLIND SPOT (6.7x SKILL.md)
  Scripts/:            3767.6 KB
  GRAND TOTAL:         9803.2 KB (~2.5M tokens)
  Hidden refs >10KB:   28 skills
  Categories: {'coding': 31, 'novel': 30, ...}
```

> 本应用自带 5 个内置技能（novel-writer / novel-deslop / novel-structure-quality-coordinator /
> skill-creator / token-optimizer），实际数字以**当场跑出的输出**为准，不要复述上面这段样本。

**关键发现**：references/ 目录占总权重 53.6%，是 SKILL.md 自身的 6.7 倍——这是此前审计的完全盲区。

### 1.3 输出控制指令

在对话中直接使用以下指令约束 agent 行为：

- **"简洁模式"** --- 将输出长度缩减 50%，只保留核心信息
- **"表格优先"** --- 仅在用户要求表格且资料契约允许时使用，不应用于小说资料的默认生成
- **"按需展开"** --- 先给结论，用户追问时再展开细节

## 二、模块 B：Skill 健康检查与精简

### 2.1 Skill 大小阈值

| 大小 | 等级 | 操作 |
|------|------|------|
| < 15KB | OK 健康 | 无需处理 |
| 15-25KB | NOTE 注意 | 检查是否可精简 |
| 25-35KB | WARN 警告 | 执行精简流程 |
| 35-50KB | CRIT 严重 | 必须精简或拆分 |
| 50-100KB | EMERG 紧急 | 立即拆分或淘汰 |
| > 100KB | BLOAT 膨胀 | 强制拆分 |

### 2.2 全目录健康检查（V9 升级）

```bash
python scripts/skill_size_check.py
```

输出包含：
- 每个 Skill 的 MD / references / scripts / assets 分项大小
- 隐藏权重标记（references > 10KB 时标注 HIDDEN）
- 内容密度分析（可执行行占比，检测哲学性/非操作性内容）
- 分层 triage 建议（BLOAT -> EMERG -> CRIT -> WARN -> NOTE -> OK，与 2.1 阈值表同一套等级）

### 2.3 Skill 精简四步流程

```
第一步：删除重复
  检查是否存在与已有 Skill 重叠的功能 -> 删除重叠部分
  多个 Skill 共享同一子功能 -> 合并到最相关的 Skill

第二步：删除冗余
  删除仅作为"说明/解释"但无操作指令的段落
  删除反复出现的标签/标记（如"自由版""建议值""用户可覆盖"）
  删除无法在运行时执行的权限体系描述

第三步：精简指令
  每个段落要么是"做X"，要么是"为什么做X"，不要"系统建议做X"
  按任务契约选择格式，用指令示例澄清流程；小说资料保持自然段与必要机器字段

第四步：评估
  对比精简前后大小 -> 确认功能无丢失 -> 更新版本号
```

### 2.4 Skill 淘汰/合并判定

以下条件满足 2 项以上，建议合并或淘汰：
- 最近 30 天触发次数 < 3
- 功能与另一个 Skill 重叠 > 60%
- Skill 文件 > 35KB 且无法精简
- Token 投入产出比（IO 质量提升 / 额外 Token） < 0.3

## 三、模块 C：缓存策略与能量模式

### 3.1 缓存优化三原则

| 原则 | 操作 | 预期效果 |
|------|------|----------|
| **前缀固定化** | 系统指令、Skill 上下文放在 Prompt 开头 | 命中率 +30-50% |
| **变量后置化** | 用户输入、动态内容放在 Prompt 末尾 | 命中率 +10-20% |
| **模板标准化** | 常用输出结构（报告、分析、列表）使用固定框架 | 命中率 +15-25% |

### 3.2 三级能量模式（V9 可执行引擎）

```bash
python scripts/energy_mode.py [context_budget_kb]
```

| 模式 | 触发条件 | 行为 |
|------|----------|------|
| **NORMAL** | > 70% 上下文预算剩余 | 全量加载、完整审计 |
| **EFFICIENT** | 40-70% 上下文预算剩余 | 仅加载领域核心 Skill，快速审计 |
| **ECO** | < 40% 上下文预算剩余 | 仅加载必须 Skill，激进压缩，最大输出行限制 |

V9 的能量模式引擎自动检测主导领域（coding/novel/finance/office/ai），输出领域特化的上下文预算建议和 Skill 加载推荐清单。

### 3.3 缓存策略检查

```bash
python scripts/cache_check.py
```

输出包括：
- 当前推荐缓存层级（L1/L2/L3）
- 前缀固化度分析（检测 cache-unfriendly 模式）
- 领域特化优化建议

## 四、模块 D：重复 Skill 检测（V9 新增 P0）

```bash
python scripts/duplicate_detect.py
```

### 检测维度

| 维度 | 权重 | 方法 |
|------|------|------|
| 名称相似度 | 0.5 | 规范化后字符集 Jaccard 相似度 |
| 描述重叠度 | 0.3 | 关键词集合交集比 |
| 组合匹配 | 0.2 | 名称+描述双维度交叉验证 |
| 指纹相同 | 1.0 | MD5 指纹唯一性判定 |

### 风险等级

| 分数 | 风险 | 操作 |
|------|------|------|
| >= 0.9 | HIGH | 保留一个，移除重复 |
| 0.7-0.9 | MEDIUM | 合并重叠功能或明确差异化 |
| 0.5-0.7 | LOW | 人工复核，可能为误报 |

## 五、模块 E：内容密度分析（V9 新增 P1）

在 `skill_size_check.py` 中集成，分析 Skill 内容的"可操作性密度"：

- **高密度**（> 60%）：以指令/代码/表格为主的实操型 Skill
- **中密度**（40-60%）：混合型
- **低密度**（< 40%）：以哲学阐述/理论框架/建议为主的说明型 Skill

检测标记包括：哲学性表述、理论框架、无执行建议、弹性因子、权限体系描述等非操作性内容。

## 六、模块 F：小说写作专项审计（V9 新增 P2）

```bash
python scripts/novel_audit.py
```

### 检测维度

| 风险类型 | 检测内容 | 严重度 |
|----------|----------|--------|
| 上下文膨胀 | 全文/所有章节/所有角色信息一次性加载请求 | HIGH |
| 公式重复 | 重复的结构性模板（"第一步...第二步..."循环） | MEDIUM |
| 角色缓存膨胀 | >3 个角色档案/设定同时存在于上下文 | MEDIUM |
| 章节结构问题 | 逐章全量上下文引用、显式记忆保持指令 | LOW |

### 小说渐进压缩策略

```
CHAPTER RANGE    CACHE LEVEL    STRATEGY
Chapter 1-5      L1 (shallow)   全文 + 角色设定
Chapter 6-15     L2 (moderate)  章节摘要 + 活跃POV角色
Chapter 16-30    L2 (moderate)  章节摘要，压缩角色设定
Chapter 31+      L3 (deep)      场景摘要，最小角色信息
```

检查点动作：
- L1->L2：摘要化第 1-5 章，丢弃非活跃角色详情
- L2->L3：归档第 6-30 章为情节摘要，仅保留当前活跃场景上下文

### 通用性设计

对于未知来源的小说类 Skill（如网络 marketplace 安装的第三方 Skill），系统通过关键词匹配自动分类（novel/coding/finance/office/ai），无需预先注册 Skill 列表。

## 七、审计发现的沉淀（本应用内可落地的做法）

**本技能只做 Token 效率优化，不依赖任何外部技能**：应用内置的技能只有 novel-writer /
novel-deslop / novel-structure-quality-coordinator / skill-creator / token-optimizer 五个，
需要别的能力时用 `skill_lookup` 看当前实际有哪些（不要按记忆里的名字去调）。

审计结论要沉淀时，落到本应用**真实存在**的位置：

| 触发事件 | 本技能动作 | 沉淀落点（用 file_write） |
|----------|-----------|--------------------------|
| 命令/脚本执行失败 | 检查是否因 Token 截断或上下文超限导致 | 作品内 `小说资料/00-项目状态.md`（阶段性结论）或直接汇报给用户 |
| 用户纠正浪费模式 | 复核是哪一类浪费模式被触发 | 作品内 `小说资料/06-写作规则.md`（经用户确认后追加，见 novel-writer 的个人文风流程） |
| 发现可复用的优化模式 | 执行优化并记录前后对比 | 汇报给用户，由用户决定是否写进写作规则；**不自行改用户的规则文档** |
| 周期性复盘 | 输出 Token 消耗趋势报表（`token_audit.py`） | 报表直接贴给用户；长期档案由用户自己保管 |

**报告纪律**：本技能的脚本只读不写（不碰作品文件）。要让结论变成长期规则，
必须走 novel-writer 的「个人文风晋升」流程（`question` 逐条确认后写进 06-写作规则）。
