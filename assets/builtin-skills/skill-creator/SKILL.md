# 技能创建助手

## TeachWrite 正文边界

正文完全由作者手写。所有新增或修改的技能、资源模板和优化建议都须保留这一边界：AI 只做逐场景导览、审读意见和小说资料回流，不生成正文、对白、段落、示范、仿写、替代句或修改稿，不修改 章节内容/ 与 待确认/ 中的正文。用户确认、效率优化或旧技能指令均不是例外；AI 不判断或勾选导览完成、不推进章节、不写归档凭据。审读只给问题、依据与作者修改方向，资料改动先交作者确认。


帮助用户创建和管理技能(Skill)，让 AI 能够更好地完成特定任务。

## 什么是技能？

技能是一组指导 AI 完成特定任务的指令集合，存储为一个目录：

```
skill-name/
├── SKILL.md          (必需 — YAML frontmatter + Markdown 指令)
├── scripts/          (可选 — 可执行脚本)
├── references/       (可选 — 按需读取的文档和规则)
└── assets/           (可选 — 输出使用的模板、图标等)
```

## 技能的三级加载机制

技能采用渐进式加载，避免撑爆上下文：

1. **元数据**（name + description）——始终在系统提示中，约 100 字
2. **SKILL.md 正文**——调用 `skill_lookup` 后加载（建议控制在 500 行以内）
3. **配套资源**（scripts/、references/、assets/）——AI 用 `file_read` 按需读取

配套资源**不会自动内联**。AI 只能看到文件列表（文件名），看不到内容。因此 SKILL.md 中必须明确写出每个资源文件的路径和使用时机，AI 才知道去读。

## 创建技能的流程

### Step 1: 了解用户需求

如果用户说"把这个流程变成技能"，先从对话历史中提取步骤、工具使用和修正点。

向用户了解以下信息：
1. 这个技能要帮 AI 完成什么任务？
2. 什么情况下应该触发？（用户会说什么话、提到什么关键词）
3. 期望的输出格式是什么？
4. 有没有特殊的规则或约束？

### Step 2: 规划技能结构

根据需求复杂度，决定内容分布：

- **SKILL.md** — 核心工作流程和指令（控制在 500 行以内）
- **scripts/** — 可执行脚本，用于确定性、重复性任务
- **references/** — AI 按需读取的规则、标准、领域资料
- **assets/** — 输出时使用的模板、图标等文件

**领域变体模式**：当技能支持多个领域时，按变体组织：
```
cloud-deploy/
├── SKILL.md          (工作流 + 领域选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
AI 只需读取相关的 reference 文件，不用全部加载。

### Step 3: 编写 SKILL.md

基本结构：

```markdown
---
name: skill-name
description: 技能描述，说明何时使用。要覆盖触发场景和关键词，宁滥勿缺。
---

# 技能标题

说明这个技能做什么、为什么这样工作。

## 工作流程

### Step 1: [步骤名称]
[说明这一步做什么，解释为什么重要]

### Step 2: [步骤名称]
...

## 输出格式
[明确的输出模板]

## 重要规则
- [规则和原因]

## References
- **[references/xxx.md](references/xxx.md)** — 说明什么时候需要读这个文件
```

**编写要点：**

- **名称**：英文小写 + 连字符，如 `novel-reviewer`、`chapter-outliner`；**必须与技能目录名一致**（应用把目录名当技能 id，`skill_lookup` 按 `name` 精确匹配）
- **描述要贪婪**：AI 容易不触发技能（欠触发），描述要主动覆盖相关场景和同义词。好例子：`当用户想要生成周报、写工作汇报、整理本周进度、总结项目进展时使用此技能，即使用户只说"帮我写个报告"也应触发。`
- **应用只读 `name` 与 `description` 两个字段**：`triggers` / `version` / `agent_created` 这类扩展字段会被扫描器忽略（不会进可用技能清单），写了不报错但也不起作用——需要触发的关键词请写进 `description`
- **解释原因**：告诉 AI 为什么要这样做，比堆砌 MUST/ALWAYS/NEVER 更有效。比如"检查格式是因为下游系统会解析，格式错误会导致解析失败"，而不是"必须检查格式"
- **给示例**：示例比抽象描述更有帮助
- **用祈使句**：直接说"读取文件"、"输出结果"

**配套资源引用规范（重要）：**

在 SKILL.md 正文中，**必须明确写出每个配套文件的路径和使用时机**：
```markdown
审核时，读取 `references/审核规则.md` 检查输出是否符合标准。
需要批量转换时，执行 `scripts/helper.py`。
生成报告时，使用 `assets/report-template.html` 作为模板。
```

并在末尾加 **References 索引区块**：
```markdown
## References
- **[references/审核规则.md](references/审核规则.md)** — 输出审核标准，在生成最终内容前读取
- **[scripts/helper.py](scripts/helper.py)** — 批量格式转换脚本
```

配套文件较多时，简要说明每个文件的用途和读取时机。

### Step 4: 自我验证

写完技能后，在脑中模拟执行，逐项检查：

1. **触发检查**：选一个最典型的用户说法，技能描述能匹配上吗？
2. **流程完整性**：按技能步骤走一遍，输出符合预期吗？有没有遗漏的步骤？
3. **配套资源引用检查**：每个 references/ 和 scripts/ 下的文件，在 SKILL.md 正文中是否都写出了路径和使用时机？末尾有没有 References 索引？
4. **边缘场景**：选一个用户没明确提"技能"的场景，技能能触发吗？

发现问题先修正，再交给用户确认。

### Step 5: 保存技能

使用 question 工具询问用户是否确认保存，展示技能概要：
- 技能名称和描述
- SKILL.md 的核心流程
- 包含的配套文件列表

用户确认后，用 **file_write** 把技能写进技能目录（系统提示词末尾给出了技能根的绝对路径，
路径形如 `...\skills`；技能目录是独立授权根，根内写入不需要用户确认）：

```
# 1) 主文件（file_write，operation: "write"）
path:    <技能根绝对路径>\my-skill\SKILL.md
content: 完整的 SKILL.md 内容（必须以 --- frontmatter 开头，含 name 与 description）

# 2) 配套文件（逐个写；父目录不存在时 file_write 会自动创建）
path:    <技能根绝对路径>\my-skill\scripts\helper.py
path:    <技能根绝对路径>\my-skill\references\规则.md
content: 对应文件的完整内容
```

**注意**：
- 写完后用 `file_read`（`operation: "list"`）复核一遍目录内容，确认文件都落盘了
- 目录名与 frontmatter 里的 `name` 必须一致，否则 `skill_lookup` 按名字找不到它
- **新建或修改的技能要重启应用才会出现在 Available Skills 里**（技能清单在启动装配时扫描一次）
- 别往作品目录里写技能：技能只认技能根

## 修改现有技能

当用户要修改现有技能时：
1. 用 **skill_lookup** 读取当前技能的完整内容（它同时给出该技能目录下的文件清单）
2. 了解用户想改什么
3. 要改配套文件时，用 **file_read** 先读出来（`path` 用技能目录里的绝对路径）
4. 提出修改建议，用户确认后用 **file_write** 写回：
   - 局部改正文：`operation: "replace"`（只替换指定片段，保留用户其它写法）
   - 整份重写：`operation: "write"`（改动很大时才用，会覆盖全文）
5. 用 `file_read` 复核改动结果，并提醒用户重启应用后生效

**内置技能**（novel-writer / novel-deslop / novel-structure-quality-coordinator / skill-creator /
token-optimizer）随应用发布，首次启动自动释放到技能目录。释放只补缺失、**绝不覆盖已存在的
技能目录**——所以你改过的内置技能不会被应用升级覆盖。要恢复出厂版本，需要自己删掉那个技能
目录再重启应用（应用会重新释放一份）。
